# DevSphere Project Review Template

Use this template for a **Project Review Friday** submission or any focused feedback request in [Project Showcase](https://github.com/Sumit-tech01/DevSphere-Community/discussions/categories/project-showcase). Copy the relevant sections into a new discussion.

> **One project, one question.** A review is most useful when the builder names the decision they are stuck on. A link drop is not a review request.

## Before posting

- Choose **one** project and **one** specific question.
- Confirm the repository, demo, or download link opens in a private browser window.
- Remove credentials, private customer data, and unpublished third-party material.
- Decide whether you want feedback only or also want collaborators.
- Disclose a commercial interest, affiliation, or sponsorship.
- If you are a minor, get a parent or guardian's permission before posting personal details.
- Read the [Community Guidelines](../COMMUNITY_GUIDELINES.md) and [Code of Conduct](../../CODE_OF_CONDUCT.md).

## Submission template

### Title

`Project Review Friday — [project name]`

### 1. Project basics

- **One-sentence description:**
- **Who it helps:**
- **Stage:** idea, prototype, MVP, live, or maintained
- **Repository or demo:**
- **License:**
- **Your role:** creator, maintainer, contributor, or other

### 2. What it does

Explain the problem and the current solution in a short paragraph. Include a screenshot or short demo only if it helps someone understand the question.

### 3. The one question

What specific decision, flow, or piece of code should reviewers focus on?

Examples of reviewable questions:

- "Is the empty state clear to someone opening the app for the first time?"
- "Can the filter controls be used with a keyboard alone?"
- "Is the README missing information that would stop someone from running the project?"
- "Is this data model going to make the next feature harder to add?"

### 4. What is working and what is limited

- **What you have already tried:**
- **What works today:**
- **Known limitations:**
- **Constraints:** time, platform, budget, compatibility, or scope

### 5. Technology and setup

- **Stack:**
- **How to run it locally:**
- **Test coverage or manual checks:**
- **Any account, key, or paid service needed to try it:**

Do not include real credentials. Use sample data or a local setup.

### 6. Safety and privacy check

- [ ] No passwords, tokens, private keys, or `.env` contents are included.
- [ ] No customer data, private messages, or personal information is included.
- [ ] The demo uses sample data or clearly marked test data.
- [ ] I have permission to share the code and screenshots.
- [ ] The project link is public or access has been arranged with the host.
- [ ] I have disclosed any commercial interest or affiliation.

### 7. What kind of response you want

- [ ] Usability
- [ ] Accessibility
- [ ] Performance
- [ ] Code structure and maintainability
- [ ] Documentation and onboarding
- [ ] Naming, positioning, or scope
- [ ] Feedback only
- [ ] Also open to collaborators

## Reviewer response template

Use four short sections. A review can be a few sentences; it does not need to be exhaustive.

### What works

Name one or two specific things that are effective, and say why.

### Questions

Ask about assumptions, constraints, or decisions you do not understand. Do not assume the builder made a mistake before asking.

### Suggestions

Offer one or two concrete changes. For each one, include a reason and a trade-off.

### Suggested next step

Name the smallest useful thing the builder could do next. The builder decides whether to accept it.

## Host checklist

- [ ] The submission contains one project, one question, and working links.
- [ ] The thread is in **Project Showcase**.
- [ ] The project is safe to open and contains no credentials or private data.
- [ ] At least one reviewer is available.
- [ ] The review format is shared in the thread.
- [ ] The builder is invited to respond, not required to defend every choice.
- [ ] Repeated feedback is consolidated instead of dogpiled.
- [ ] The thread is summarized when it becomes long.
- [ ] No one is ranked or compared.

## Review etiquette

- Critique the work, not the person.
- Ask before rewriting someone's project.
- Do not demand unpaid labor or a merge.
- Do not use the thread to recruit, sell, or promote an unrelated product.
- Do not share private code, credentials, or customer data.
- Respect the builder's stated scope and constraints.
- If you cannot be specific and kind, wait until you can.
