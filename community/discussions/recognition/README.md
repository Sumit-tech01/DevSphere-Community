## Why these categories

DevSphere uses the existing 12-category structure. No new category is required.

| Need | Existing category | Reason |
| --- | --- | --- |
| Official program announcement | **Announcements** | Maintainer-controlled official updates; members can reply |
| Nominations and questions | **General Discussion** | Open to every member and easy to find |
| Project feedback | **Project Showcase** | The category is already for sharing work and requesting feedback |
| Recognition posts | **Announcements** | Official recognition with a stable, visible home |
| Teammate matching | **Collaboration** | The category is already for projects, teammates, and reviews |

Do not create a `Spotlight` category just for these posts. That would add a 13th category, fragment the conversation, and break the verified category architecture.

## Before publishing

- [ ] Confirm the post is not a duplicate of a live discussion.
- [ ] Confirm the category exists and uses the correct format.
- [ ] Create or verify the labels.
- [ ] Open every link in a private browser window.
- [ ] Confirm the handbook and templates are live in the repository.
- [ ] Decide who will respond to comments and for how long.
- [ ] Remove the hidden metadata comment if the publishing tool does not do it automatically. It is invisible on GitHub, but it is not part of the public post.
- [ ] Publish manually. Do not schedule an automatic post.
- [ ] Update this file's status table after publication.
- [ ] Pin only if the post is a durable entry point; keep the pinned set small.

## After publishing

- Reply to questions with specific answers, not just links.
- Do not announce a spotlight or Builder of the Month recipient before the person has approved the draft.
- If a post receives no response, ask why before reposting it.
- Archive outdated threads with a final status note rather than deleting them.
- Record changes in the [changelog](../../../CHANGELOG.md) when they affect the program structure.
