# 🔍 Project Review Friday — Share a Project, Get Useful Feedback

Building in public is easier when someone looks at the work and tells you something specific. **Project Review Friday** is a weekly thread for exactly that.

It is not a roast, a score, or a popularity contest. The goal is one or two changes you can actually make.

## How to submit a project

1. Choose **one** project and **one** specific question.
2. Open a new Project Showcase discussion titled `Project Review Friday — <project name>`.
3. Include context, links, and the part you want reviewed.
4. Use the [project review template](https://github.com/Sumit-tech01/DevSphere-Community/blob/main/community/templates/PROJECT_REVIEW_TEMPLATE.md) as a base.
5. Do not post only a link. A link drop is not a review request.

### What to include

- What the project does and who it helps.
- A working demo or repository link.
- The current stage: idea, prototype, MVP, live, or maintained.
- The technology stack and any constraints.
- Known limitations.
- The specific feedback you want: usability, accessibility, performance, code structure, documentation, naming, or positioning.
- Whether you want collaborators or only feedback.

### Example request

> I built a small tool that turns a CSV into a searchable table. It works with my test file, but I am not sure the empty state makes sense. I would like feedback on onboarding and keyboard navigation. The repo is public, the demo uses sample data, and I am not looking for collaborators yet.

That is reviewable. "Check out my app" is not.

## How to review

Use four short sections:

| Section | What to write |
| --- | --- |
| **What works** | Name one or two specific things that are effective. |
| **Questions** | Ask about assumptions, constraints, or decisions you do not understand. |
| **Suggestions** | Offer one or two concrete changes, with a reason and a trade-off. |
| **Suggested next step** | Name the smallest useful thing the builder could do next. |

A short review is welcome. This is more useful than generic praise:

> "The README explains the problem clearly. I would add a screenshot of the empty state because that is where I got stuck. The keyboard focus is visible on the table but not on the filter button. A next step could be a five-minute accessibility pass with the keyboard only."

## Review etiquette

- Critique the work, not the person.
- Ask before rewriting someone's project.
- Do not demand unpaid labor or a merge.
- Do not use the thread to recruit, sell, or promote an unrelated product.
- Do not share private code, credentials, or customer data.
- Do not dogpile. If several reviewers agree, consolidate instead of repeating.
- Respect the builder's stated scope and constraints.
- If you cannot be kind and specific, wait until you can.

## Host rhythm

- The host opens a thread on Friday at 09:00 UTC when a reviewer is available.
- Submissions stay open through the following week.
- The host invites at least one reviewer per project.
- The host summarizes repeated themes when a thread becomes long.
- The host closes the loop: what changed, what was tried, what remains.
- A Friday with no submissions or no reviewers is skipped, not filled with invented content.

## What this program is not

It is not a certification, a ranking, a guarantee of users, or a promise of employment. A review is one perspective, not a verdict. The builder decides what to accept.
