# DevSphere Community Activities

A recurring rhythm helps a community stay useful without turning participation into a second job. This page describes the activities DevSphere can run, the discussion category for each, and the template to use.

> **Honest status:** these are proposed formats, not a promise that every activity runs every week. DevSphere has a small volunteer capacity. An activity happens when a host publishes it, there is a real discussion to have, and moderation is available. No member should feel guilty for missing a week.

### What each weekly activity includes

#### Monday — Weekly learning goals

A short accountability thread. Members share:

- One skill they are learning.
- One small deliverable for the week.
- One blocker they expect.
- One resource that has helped.

The host replies with encouragement and connects people working on similar topics. This is not a streak contest.

#### Tuesday — Technical deep dive

One focused question, such as:

- Why does this query become slow at scale?
- When should a feature use a queue instead of a synchronous request?
- How do you test an accessibility interaction?
- What trade-off did you make in a recent project?

The host provides context and asks members to explain reasoning, not just drop opinions.

#### Wednesday — AI & ML discussion

A paper, tool, benchmark, or evaluation question. Every discussion should distinguish:

- What was measured.
- What was not measured.
- What data was used and whether it was appropriate.
- What the limitations are.
- What a responsible deployment would require.

Do not present a demo as evidence of general capability.

#### Thursday — Coding challenge

Use the existing [challenge system](../challenges/README.md). A challenge thread includes:

- Problem statement and constraints.
- Definition of done.
- Suggested level and time range, not a deadline pressure.
- Submission location in Project Showcase.
- Feedback expectations.

Members should not post full solutions to active challenges without a spoiler warning.

#### Friday — Project Review Friday

A structured feedback thread:

- One project and one specific review question per submission.
- Context, a working link, the current stage, and known limitations.
- Feedback in four parts: what works, questions, suggestions, and one next step.
- A builder response that closes the loop on what changed.

Follow the [Project Review Friday format](COMMUNITY_INITIATIVES.md#b-project-review-friday). Critique the work, not the person, and do not demand unpaid labor. Open-source help remains welcome in [Collaboration](https://github.com/Sumit-tech01/DevSphere-Community/discussions/categories/collaboration); read the [Open-Source Guide](OPEN_SOURCE_GUIDE.md) before offering a contribution.

#### Saturday — Project showcase

A showcase is a structured request for feedback, not a link drop. Use the [project showcase template](templates/PROJECT_SHOWCASE.md). The host asks at least one specific question about each project.

#### Sunday — Community feedback

One small improvement question:

- What helped you this week?
- What was confusing?
- Which category is hard to use?
- What should we stop doing?
- Who should we thank?

The host records actionable feedback and follows up. Feedback without follow-up becomes noise.

### Build sprint

A build sprint is a short, self-directed period for finishing a small milestone. It is not a competition and has no prize unless a sponsor explicitly provides one in writing.

A sprint post includes:

- The problem and intended user.
- The smallest deliverable.
- Start and end dates.
- What the builder will share at the end.
- Where progress updates will go.
- Whether collaborators are welcome and under what terms.

### Developer Spotlight

Use the [Developer Spotlight](DEVELOPER_SPOTLIGHT.md) framework and the [Community Initiatives](COMMUNITY_INITIATIVES.md) program map. No one is featured without permission and verifiable evidence. The weekly slot is a rhythm, not a quota; there is no obligation to publish a profile to fill a week.

### Builder of the Month

Use the same evidence and consent rules as the Spotlight. Recognize meaningful contribution, learning progress, or project development. There is no prize, ranking, or requirement to choose a recipient every month. Read the [Builder of the Month format](COMMUNITY_INITIATIVES.md#c-builder-of-the-month).

### Open-source contribution month

Members share contributions they are proud of and what they learned. The community does not rank people by commit count, lines changed, or merged pull requests. A documentation fix can be more valuable than a large, unreviewed change.

### Knowledge-sharing session

A session can be a written explainer, a short walkthrough, or a live discussion. If it is recorded, obtain consent from every speaker and avoid showing private data. Publish a summary even when a recording is unavailable.

### Collaboration week

A focused period for proposals and teammate matching. Use the [project proposal](templates/PROJECT_PROPOSAL.md), [find a teammate](templates/FIND_A_TEAMMATE.md), and [collaboration request](templates/COLLABORATION_REQUEST.md) templates. The goal is a small first milestone, not a promise of a finished product.

## Host checklist

Before publishing an activity:

- [ ] The activity has one clear purpose and one clear action.
- [ ] The category is correct.
- [ ] The post includes context, not only a link.
- [ ] The time commitment is stated honestly.
- [ ] Accessibility is considered: descriptive links, alt text, readable formatting.
- [ ] The activity does not require a paid tool.
- [ ] There is a moderation plan for sensitive topics.
- [ ] A follow-up date is stated, even if the answer is "no update yet."
- [ ] Any opportunity is labeled paid, unpaid, or voluntary.
- [ ] No member, statistic, partner, or achievement is invented.

## Facilitation principles

1. **Make it easy to participate quietly.** A thoughtful reply is participation; not everyone wants to be on camera or share a goal publicly.
2. **Respect time zones.** Use asynchronous posts and state deadlines in UTC.
3. **Do not reward volume.** Recognize specificity, kindness, and usefulness.
4. **Protect beginners.** "Beginner-friendly" means the host provides context and does not mock questions.
5. **Close the loop.** Summarize what was decided and where it was recorded.
6. **Skip when capacity is low.** A canceled activity is better than a neglected thread.
7. **Archive thoughtfully.** Link old activities in new ones when useful, but do not bump dead threads for engagement.
8. **No engagement bait.** Do not manufacture controversy, fake urgency, or false scarcity.
